# Portable Scope Binding

## 상태

accepted for 1.1.0 release. 적용 범위와 1.1.0 버전은 사용자 확인으로 확정됐으며 저장·호스트 연결은 구현됐다. 후속 배포 승인은 아래에 별도로 기록한다. 문서 경로는 기존 참조 보존을 위해 유지한다.

- 작성 계기: 코드 관찰과 반복된 범위 연결 설계 검토.
- 관찰 근거: `src/cli/context-preview.ts`의 `previewFromSources`,
  `src/cli/context-personalization.ts`의 `readContextPersonalization`,
  `src/config/context-config.ts`의 `CONTEXT_CONFIG_KEYS`,
  `packages/shared-skills/skills/philosophy-refinement/references/persistence.md`.
- 확정된 적용 범위·배포 승인과 실제 게시 증거를 구분한다. 이 문서 자체가
  실행 권한이나 실제 호스트 검증 증거를 만들지는 않는다.
- 사용자 확인: 2026-09-07, 현재 체크아웃에만 적용하며 다른 worktree·복제본에는
  새 연결 승인이 필요하다고 선택했다. 이 범위 결정을 다시 질문하지 않는다.
- 추가 사용자 확인: 새 세션에서는 같은 작업을 명시적으로 재개할 때만 작업 결정을
  재적용한다. 해당 체크아웃의 마지막 작업을 자동으로 재개하지 않는다.
- 버전 확인: 사용자가 `1.1.0 로컬 후보로 정합성 맞추기`를 승인했다.
  당시 승인은 원격 배포를 포함하지 않았다.
- 후속 확인: 사용자가 `배포까지 다 진행해`라고 명시적으로 승인했다.
  1.1.0의 commit·PR·merge·immutable tag·npm latest·GitHub Release를 기존
  보호 게이트에 따라 진행한다. 검토·CI·registry 확인을 생략하는 승인은 아니다.

## 문제 상황

현재 개인 저장소의 프로젝트·작업 규칙은 임의의 승인된 key를 쓴다.
Preview와 전달 코어는 명시적인 project/task selector를 지원하지만,
검토 시작 당시 휴대형 호스트가 현재 체크아웃·작업을 그 key에 연결하는 저장
계약은 없었다. 현재 체크아웃 연결은 아래와 같이 로컬 구현했다.
디렉터리 이름, 브랜치 이름, 유일한 규칙이라는 이유로 연결하면 다른
프로젝트나 다음 작업에 승인 범위를 넘겨 적용할 수 있다.

프로젝트 연결은 현재 체크아웃에 한정하거나 같은 Git 저장소의 worktree에
공유할 수 있다. 후자는 공유 승인 범위와 worktree별 예외 정책이 추가된다.
작업은 호스트 세션과 같지 않다. 한 세션에서 다른 작업을 시작할 수 있으므로
세션 식별자만으로 작업 결정을 영구 적용할 수 없다.

## 선택한 방향

제안은 명시적인 최초 연결 승인과 좁은 기본 범위다.

- 개인 규칙의 기존 자동 선택 경로는 그대로 둔다.
- 프로젝트 규칙 key는 실제 사용자가 승인한 체크아웃 연결을 통해 재사용한다.
  같은 Git 저장소의 다른 worktree에 자동 확장하지 않는 안을 기본 제안으로 둔다.
- 작업 연결은 프로젝트 연결과 별개다. 활성 작업을 명시적으로 선택하고,
  작업 전환·종료 시 해제한다. 재개·압축만으로 연결을 바꾸지 않는다.
  새 세션에는 마지막 작업을 자동 연결하지 않으며 명시적인 동일 작업 재개가 필요하다.
- 기존 프로필 V1의 rule scope와 이력을 재작성하지 않는다. 경로·호스트
  식별자를 기존 provenance나 rule text에 끼워 넣지 않는다.
- 새 연결 저장소는 버전과 엄격한 필드 검사를 갖추고, 필요한 식별 digest와
  승인된 scope key만 기록하는 방향으로 설계한다. 원문 경로나 대화는 저장하지 않는다.
- 연결 부재·불일치·손상은 scoped rule 미적용과 명시적 진단으로 처리한다.
  기존 context 비활성화, 경로 소유권, host trust, Finish 권한은 바꾸지 않는다.

확정된 체크아웃 범위를 따라 `context scope`의 조회·bind·unbind와 개인 설정
위치의 `project-bindings/<digest>.json`을 구현했다. 공개 record 버전은
`persona-context-checkout-binding.1`이며 기존 프로필 V1은 변경하지 않는다.
실제 사용자 설정에 연결을 만들지 않았고 격리된 fixture만 사용했다.
작업 연결은 `context task --session <handle>` 조회, 명시적 `resume --task <key>`,
`end --task <key>` 및 읽기 전용 `preview`로 구현했다. 호스트 namespace와
실제 hook session_id의 digest를 handle로 쓰되, 작업 key는 명시적으로 선택한다.
`task-bindings/<digest>.json`은 현재 체크아웃과 handle에 한정된 연결이며
프로필 V1과 프로젝트 연결을 다시 쓰지 않는다. 새 세션에는 연결이 없다.
작업 전환·완료·취소의 자연어 판단과 end 실행은 모델 지침이며 호스트 강제는 아니다.
Codex Luna Max의 한 격리 관찰에서 재개·편집 전 작업 Preview·검사·종료를 확인했다.
정상 호스트 일회성 쓰기 승인이 필요했으며 일반적 준수나 Claude 실사용 증거는 아니다.
새 공개 API를 포함하는 로컬 후보 버전은 사용자 승인에 따라 1.1.0이다.

## 선택 이유

### 기존 계약 재사용

연결된 key를 기존 `ContextRelevance`에 전달하면 동일한 계층·범위 해석기를
사용할 수 있다. 새 철학 저장소나 별도 우선순위 해석기는 필요 없다.

### 승인 범위 보존

프로젝트 경로 추정과 호스트 세션의 작업 간 재사용을 분리해야 승인하지 않은
대상으로 규칙이 퍼지는 것을 막을 수 있다. 연결은 실행 권한이 아닌 관련성이다.

---

## 트레이드오프

체크아웃별 연결은 worktree를 많이 쓰는 사용자에게 최초 연결 동의를 추가한다.
활성 작업 수명주기도 정해야 하므로 단순한 전역 taskKey 설정으로 끝낼 수 없다.
새 공개 설정이나 명령이 생기면 이 변화는 기존 1.0.1 패치 후보에 숨기지 않는다.
사용자의 별도 1.1.0 승인만 로컬 버전 정합성 변경의 근거이며 이 문서는 배포 권한을 만들지 않는다.

---

## 현재 판단

현재 프로젝트 연결은 최초 명시적 동의 후 자동 재사용되는 로컬 구현이다.
태스크 연결은 로컬·설치 경계와 실제 모델 관찰을 구분한다. 의미 보완은 별도 새 스키마 없이 기존 승인된 통합 후보와
`supersede` 절차로 처리할 수 있으며, 해당 저장·Preview·전달 경로는
`tests/context-personal-scope.test.ts`에서 검증했다. 이는 모델의 의미 판단을
검증한 것이 아니며 scope 연결 완료를 대신하지 않는다.

---

## 재검토 신호

- 사용자가 현재 체크아웃 한정 결정을 명시적으로 바꾸고 worktree 공유를 요청한다.
- 호스트가 세션과 구분되는 안정적인 작업 식별·전환 이벤트를 제공한다.
- 체크아웃 이동·복제 시 기존 연결 보존이 제품 요구사항으로 확정된다.
- 승인된 로컬 후보 범위를 넘어 원격 배포를 요청한다.
