# Persona Harness 1.0.0 평가와 작업 근거

## 평가 기준

기준 소스는 `19722e29ed690b2c894aeb178c7e9cc7d83ec736`의 0.13.0입니다.
작업은 [#483](https://github.com/jyt6640/persona-harness/issues/483)에서
추적합니다. 2026-09-05에 공식 Astra 가이드, 실제 소스, 공개 이슈, 설치된
Codex 설정을 대조했습니다. 이 문서는 릴리스 준비 기록이며 게시 완료를
증명하는 기록은 아닙니다.

## 강점과 개선점

| 경계 | 확인한 사실 | 1.0.0 조치 |
| --- | --- | --- |
| 철학과 컨벤션 | 프로젝트 프로필, 개인화, 승인된 결정, 관련 스킬을 분리해 보존한다. | 기존 저장과 소유권 계약을 유지하고 실제 작업에 적용하라는 공통 지침을 제공한다. |
| 작업 지속성 | 시스템 문구가 매 메시지의 새 구현 의도와 accepted plan을 요구했다. | 상태 질문과 정정을 원래 작업에 반영하고 작은 수정의 과도한 plan 요구를 제거한다. |
| 승인 재사용 | 일부 스킬은 절차별 승인과 핸드오프를 강조해 이미 승인된 작업도 멈출 여지가 있었다. | 작업 범위에 이미 포함된 구현, 검증, 리뷰를 이어간다. 범위 밖 권한은 새로 만들지 않는다. |
| 검증 비용 | 코드 변경이 아닌 일에도 test-first 문구를 일괄 적용했다. | 행동 회귀에는 테스트를 유지하고, 단순 문구 수정은 문구 자체의 snapshot으로 증명하지 않는다. |
| 호스트 이동성 | 공통 materializer가 각 호스트용 스킬 파일을 만든다. | 같은 실행 지침을 생성 경로에 연결하고 설치 산출물을 검사한다. |
| 모델 전환 | 본체는 OpenAI 요청을 직접 만들지 않는다. 운영용 최신 모델 핀은 Spark였다. | 현재 운영 핀을 Astra로 바꾸고 과거 Spark 관측·schema는 그대로 보존한다. |
| 사용자 설정 | Codex 기본 모델은 이미 Astra/medium이었다. 역할 모델은 서로 달랐다. | 기본 모델/effort를 유지하고 개인 역할 설정을 Luna Max로 정합화한다. 현재 작업은 사용자 요청대로 주 세션에서 수행한다. |
| 완료 근거 | Finish, authority, 원본 artifact 검증은 프롬프트와 별도 코드 경계이다. | 단순 지침 변경으로 완료 권한이나 검증 결과를 만들지 않는다. |
| 자동 업데이트 | OpenCode updater는 같은 major인지 확인하지 않고 모든 최신 stable pin을 적용했다. | major 변경을 쓰기 전에 차단하고 명시적 버전 선택으로만 전환하도록 교정한다. 예전 설치에는 소급되지 않음을 문서화한다. |

가장 큰 개선 대상은 모델의 성능 부족을 보완하는 긴 프롬프트가 아니라,
사용자가 이미 정한 목표를 절차가 방해하는 부분입니다. 모델명을 변경하는
것만으로 이 충돌이 해결되지는 않습니다. 반대로 질문을 없애는 것도 해결책은
아닙니다. 결과가 달라지는 미결정 요구사항은 여전히 질문해야 합니다.

## 변경된 소스 경계

- `src/runtime/skill-execution-guidance.ts`: 승인 범위, 지속 작업, 설명과 중단,
  적절한 검증에 대한 공통 지침.
- `src/cli/host-skill-materializer.ts`: 각 호스트가 발견하는 스킬에 공통 지침을
  포함한다. 패키지의 호스트 플러그인도 같은 생성 경로를 사용한다.
- `src/runtime/opencode-skill-adapter.ts`: compact route에 짧은 실행 지침을
  전달한다. 전체 카탈로그를 로드하지 않는다.
- `src/runtime/system-constitution.ts`: 현재 요청을 작업 맥락과 함께 해석하고
  승인 범위의 진단을 이어가도록 문구를 정정한다.
- `src/cli/agents-contract.ts`: 새로 생성하는 PH 관리 블록에 같은 기준을
  전달한다. 업데이트의 사용자 파일 소유권 판단은 변경하지 않는다.
- `AGENTS.md`: PH 패키지 소스 개발과 Java/Spring 소비자 개발의 차이를
  설명하고 프로젝트 검증 명령과 기여 경계를 명시한다.
- `src/cli/project-auto-update.ts`: 자동 major 변경을 config/manifest 쓰기
  전에 차단한다. 기존 explicit enable과 같은 major 업데이트는 보존한다.

## 확인된 로컬 검증

초기 변경 후 typecheck와 8개 관련 테스트 파일의 57개 테스트가 통과했습니다.
여기에는 스킬 어댑터 생성, 시스템 주입의 opt-out/중복 방지, 인터뷰 제어,
명시 요청 라우팅, 운영 계약의 모델 핀이 포함됩니다. Astra 핀 회귀는 먼저
Spark 값에서 실패한 뒤 현재 값에서 통과하는 것을 확인했습니다.

기존 시스템 테스트의 자연어 문장 일치 검사는 제거하고 실제로 쓰이는 중복
방지 marker와 기존 host prompt 보존, 주입 조건 검사를 유지했습니다. 이는
문장을 바꿔도 실제 주입 제어가 검증되도록 하는 변경입니다. 모델이 모든
문장을 따르는지는 이 테스트가 증명하지 않습니다.

전체 Vitest 실행은 399개 파일에서 2,818개 통과, 1개 실패, 1개 skip이었습니다.
실패 원인은 새 한국어 가이드가 README에 추가됐으나 패키지 정책 테스트의
예상 링크 목록에 빠진 것이었습니다. 파일 자체와 package files 등록은
존재했으며 목록을 정정한 뒤 해당 25개 검사가 모두 통과했습니다.
문서 taxonomy, release truth, release workflow 정책과 기존 provenance audit도
통과했습니다. 검토는 사용자 요청에 따라 주 세션에서 직접 수행했으며
독립 리뷰나 실제 모델 관측으로 표현하지 않습니다.

패키지 검증 후 추가 검토에서 major 승인 경계가 기존 코드에 없음을 발견했습니다.
초기 "기존 보호를 유지한다"는 판단을 철회했습니다. 1.0.0에서 2.0.0을
자동 적용하는 회귀를 재현한 뒤 쓰기 전 차단을 추가했습니다. 이 변경으로
패키지 바이트가 달라지므로 이전 정본 결과는 새 후보의 근거로 재사용하지 않습니다.

정본 패키지, PR, protected main, Release와 npm 게시 결과는 후속 candidate
freeze 및 #483의 실행 증거로 기록합니다. 로컬 결과로 최종 게시 PASS를
추론하지 않습니다.

## 남은 검증과 기존 이슈

- #475와 #410: OpenCode 실제 세션의 선택·전달 관측이 남아 있다.
- #460: 네 호스트의 실사용 수용 조건은 정적 파일 생성만으로 충족되지 않는다.
- #317: 독립 Spring 사용자의 결과 측정은 별도이다.
- #311: 기존 기술적 provenance 정리와 독립적인 source/license 검토는 다른
  조건이다. 새 버전으로 후자를 완료했다고 주장하지 않는다.
- #316: 비공개 취약점 제보 경로의 수용 조건은 별도로 유지한다.

이런 한계는 1.0.0의 배포 여부와 함께 투명하게 표시해야 합니다. 1.0.0은
모든 언어의 enforcement, 모든 호스트의 실제 동작, 토큰 절감이나 독립 사용자
성과가 증명됐다는 뜻으로 사용하지 않습니다.
